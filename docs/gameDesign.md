# 災害カードゲーム v1 ゲームデザイン案

最終更新: 2026-07-07

この文書は、現在開発中の「災害を引き起こす闇の組織」対「それを防ごうとする日本政府」の非対称カードゲームに、デュエル・マスターズ的なゲーム性を抽象化して組み込むための設計案です。

目的はデュエル・マスターズを再現することではありません。参考にするのは、以下のようなカードゲームとしての構造です。

- 手札を使うか、将来のリソースにするかの選択
- シールドによる防御層と、逆転要素
- 場に残るカードによる継続的な有利・不利
- 攻撃、ブロック、判定を通じた盤面の駆け引き

このゲームでは、それらを災害・防災・啓発というテーマに置き換えます。

---

## 1. 基本コンセプト

仮称は「防災デュエル」または「災害対策デュエル」。

2人用の非対称対戦カードゲームです。

| 陣営 | 目的 | プレイ感 |
|---|---|---|
| 闇の組織 | 被害ゲージを100にする | 災害・混乱を仕掛け、防災シールドを崩す |
| 政府 | 対策ゲージを100にする | 予算・対策・啓発で被害を抑え、社会の備えを高める |

既存の「被害ゲージ / 対策ゲージ」は残します。  
その上で、カードゲームとしての判断を増やすために、以下を追加します。

- 防災シールド
- 基盤ゾーン
- 現場レーン
- 場に残る継続カード
- 緊急対応トリガー

## 2. デュエル・マスターズ要素との対応

| 参考要素 | このゲームでの置き換え | 採用理由 |
|---|---|---|
| シールド | 防災シールド | いきなり被害ゲージに入らず、防御層をめぐる攻防を作る |
| マナゾーン | 基盤ゾーン | 手札をリソース化する選択を作る |
| クリーチャー | 継続脅威 / 防災ユニット | 場に残るカードで盤面差を作る |
| 呪文 | 災害カード / 対策カード / 啓発カード | 単発効果のカードとして扱う |
| 攻撃 | 災害・工作による被害圧力 | 闇の組織が政府側へ圧力をかける行動に変換する |
| ブロック | 防災ユニットによる対応 | 政府が被害を受け止める行動に変換する |
| S・トリガー | 緊急対応トリガー | 劣勢側の逆転と教育的なTips表示を作る |
| 召喚酔い | 配備直後は次ターンまで対応不可 | 場に残るカードの即効性を抑え、先読みを作る |
| タップ / アンタップ | 使用済み / 使用可能 | ブラウザUIではカード回転ではなく状態バッジで表現する |

用語はそのまま使いすぎない方がよいです。UI上では「攻撃」よりも「災害発生」「被害圧力」「対応」「軽減」などの表現を優先します。

## 3. 勝利条件

プロトタイプでは、既存仕様を維持します。

| 陣営 | 勝利条件 |
|---|---|
| 闇の組織 | 被害ゲージが100に到達する |
| 政府 | 対策ゲージが100に到達する |

将来的な追加候補として、以下も考えられます。

- 闇の組織: 防災シールドをすべて破壊したうえで、大型災害を通す
- 政府: 一定ターン終了時に被害ゲージを一定以下に抑える
- どちらかの山札切れを敗北条件にする

ただし、最初の拡張では山札切れ敗北は入れない方がよいです。現在の実装は捨て札を再シャッフルして山札に戻す構造であり、ゲームテンポもその方が安定します。

## 4. ゾーン設計

ブラウザUIでは、物理カードゲームほど多くのゾーンを扱うと見づらくなります。v1では以下に絞ります。

| ゾーン | 内容 | UI上の扱い |
|---|---|---|
| 山札 | 各陣営のデッキ | 枚数のみ表示 |
| 手札 | 自分が使えるカード | 自分の手札のみ実体表示、相手は枚数のみ |
| 基盤ゾーン | 手札から置いたリソース源 | 枚数と追加回復量を表示 |
| 防災シールド | 政府側の防御層 | 裏向きカードとして5枚表示 |
| 現場ゾーン | 災害・対策カードが置かれる中央の場 | 3レーンで表示 |
| 捨て札 | 使用済みカード | 枚数と直近カードを表示 |
| ログ | 行動履歴と判定結果 | 直近数件を表示 |

現在の実装には、山札・手札・捨て札・リソース・ログはすでにあります。追加の中心は次です。

- `civicShields`
- `resourceZone`
- `field.lanes`

## 5. リソース設計

現在は毎ターン、闇の組織にCP、政府に予算が+3されます。

これを少しカードゲーム寄りにするため、手札を「基盤ゾーン」に置く選択を追加します。

### 推奨ルール

毎ターン開始時:

1. 両者がカードを1枚引く
2. 両者のリソースを回復する
3. 各プレイヤーは手札から1枚まで基盤ゾーンに置ける

リソース回復量は以下にします。

```text
回復量 = 2 + 基盤ゾーンの枚数
上限 = 10
```

例:

| 基盤ゾーン枚数 | 毎ターン回復量 |
|---:|---:|
| 0枚 | +2 |
| 1枚 | +3 |
| 2枚 | +4 |
| 3枚 | +5 |

これにより、プレイヤーは次の判断を迫られます。

- 今すぐカードを使う
- 手札を温存する
- 将来のために基盤化する

完全なマナタップ制にするとUIと処理が重くなるため、最初は「基盤枚数に応じて回復量が増える」方式が現実的です。

## 6. 防災シールド

防災シールドは、このゲームに最初に追加すべき重要メカニクスです。

### 基本ルール

- ゲーム開始時、政府の山札から5枚を防災シールドとして伏せる
- 闇の組織の災害が軽減しきれなかった場合、防災シールドを1枚破壊する
- 防災シールドが残っている間は、被害ゲージへの加算を抑える
- 防災シールドが0枚になると、以後の災害は被害ゲージに直接入りやすくなる

### シールド破壊時の処理

まずは以下の単純なルールを推奨します。

```text
最終被害 > 0 かつ 防災シールドが残っている:
  防災シールドを1枚公開する
  緊急対応トリガーがあれば自動発動する
  被害ゲージへの加算は0、または半分にする

最終被害 > 0 かつ 防災シールドがない:
  最終被害を被害ゲージに加算する
```

ゲームテンポを重視するなら「シールドがあっても半分は被害ゲージへ加算」がよいです。  
デュエル・マスターズ的なシールド感を重視するなら「シールドがある間は被害ゲージ加算0」がよいです。

このプロトタイプでは、被害ゲージが動いた方が状況を理解しやすいため、以下を推奨します。

```text
防災シールドあり:
  被害ゲージ加算 = floor(最終被害 / 2)

防災シールドなし:
  被害ゲージ加算 = 最終被害
```

## 7. 緊急対応トリガー

防災シールドから公開されたカードが `emergencyTrigger` を持っている場合、自動で発動します。

| カード | トリガー効果 |
|---|---|
| 緊急避難指示 | この災害の被害を半減 |
| 備蓄キャンペーン | 対策ゲージ+5 |
| 災害情報アラート | 次の政府予算+1 |
| 地域避難訓練 | 防災ユニットを1枚引く |

プロトタイプでは「発動する / しない」を選ばせない方がよいです。

理由:

- 割り込みフェイズが増える
- WebSocket同期が複雑になる
- タイムアウト処理が必要になる
- 相手待ち時間が増える

まずは自動発動にします。

## 8. 現場ゾーンとレーン

中央の場は、災害と対策がぶつかる場所です。

ブラウザUIではレーン制にすると理解しやすくなります。

| レーン | 主なカード |
|---|---|
| 地震・建物 | 直下型地震、余震、耐震補強、家具固定 |
| 水害・気象 | ゲリラ豪雨、洪水、防潮堤、避難指示 |
| 情報・社会 | SNSデマ、流通混乱、公式情報発信、備蓄啓発 |

表示イメージ:

```text
[地震・建物]   災害カード / 継続脅威    vs    対策カード / 防災ユニット
[水害・気象]   災害カード / 継続脅威    vs    対策カード / 防災ユニット
[情報・社会]   工作カード / 混乱効果    vs    啓発カード / 広報対策
```

レーン制のメリット:

- UI上で中央の場を整理しやすい
- カード効果の対象を説明しやすい
- 「地震対策」「水害対策」「情報対策」という教育的な分類になる
- 将来的にカード追加しやすい

## 11. ターン進行

既存の `dark -> government -> resolution` 構造を維持します。

```text
1. 回復フェイズ
   - 両者がカードを1枚引く
   - CP / 予算を回復
   - 基盤ゾーンに応じて追加回復

2. 基盤フェイズ
   - 各プレイヤーは手札から1枚まで基盤ゾーンに置ける

3. 闇の組織フェイズ
   - 災害、工作、継続脅威を1枚プレイ
   - パスも可能

4. 政府対応フェイズ
   - 対策、防災ユニット、啓発を1枚プレイ
   - パスも可能

5. 判定フェイズ
   - 災害威力を計算
   - 対策で軽減
   - 防災シールドを処理
   - 緊急対応トリガーを自動処理
   - 被害ゲージ / 対策ゲージを更新
   - 勝敗判定
```

基盤フェイズは、実装上は各プレイヤーの行動フェイズ内に含めてもよいです。

例:

- 闇の組織フェイズ: 基盤化してからカードをプレイできる
- 政府対応フェイズ: 基盤化してからカードをプレイできる

この方がフェイズ数を増やさず、UIもシンプルです。

## 12. 判定計算

最初は以下の式で十分です。

```text
基本威力 = 闇の組織がこのターン出した災害の威力
継続威力 = 場に残っている継続脅威の威力
軽減量 = 政府カードの軽減値 + 対応レーンの防災ユニット軽減値

最終被害 = max(0, 基本威力 + 継続威力 - 軽減量)
```

その後、防災シールドを処理します。

```text
防災シールドが残っている場合:
  最終被害 > 0 ならシールドを1枚公開
  緊急対応トリガーがあれば自動発動
  被害ゲージ += floor(最終被害 / 2)

防災シールドがない場合:
  被害ゲージ += 最終被害
```

対策ゲージは、政府カードの効果で加算します。

```text
対策ゲージ += 政府カードの countermeasure
対策ゲージ += 緊急対応トリガーの countermeasure
```

## 13. UI / UX方針

デザインは怖すぎる方向にしません。  
「危機管理ダッシュボード + 教育カードゲーム」のトーンにします。

### 画面構成

```text
上部:
  被害ゲージ / 対策ゲージ / ターン / フェイズ / 接続状態

中央:
  防災シールド
  3つの現場レーン
  現在の災害・対策・Tips

下部左:
  闇の組織の手札、CP、基盤ゾーン

下部右:
  政府の手札、予算、基盤ゾーン
```

### UIで守ること

- 相手の手札は枚数だけ表示する
- 防災シールドは裏向きで表示する
- 防災Tipsはカード内では省略し、ポップオーバーやダイアログで全文表示する
- 「攻撃」より「災害発生」「被害圧力」「対応」「軽減」を使う
- タップ表現はカード回転ではなく「使用済み」バッジで表現する
- モバイルは非対応表示でよい
- 1画面に収めるため、手札は横スクロールでもよい

## 14. フロントエンドへの影響

主に追加される表示は以下です。

- 基盤ゾーン
- 防災シールド
- 3つの現場レーン
- 継続脅威カード
- 防災ユニットカード
- 緊急対応トリガー演出
- シールド公開演出
- 判定結果の内訳表示

フロントエンドはゲーム判定を持ちません。

フロントエンドの責務は以下に限定します。

- サーバーから受け取った `MatchView` を表示する
- 自分が可能なアクションだけボタン表示する
- 選択したカードIDと対象レーンを送信する
- WebSocketで最新状態を受け取る
- Tipsやログを見やすく表示する

## 15. GameCoreへの影響

ゲームルールの正本は `packages/game-core/src/index.ts` に置きます。

追加が必要な概念は以下です。

```ts
type Lane = "earthquake" | "flood" | "information"

type FieldCard = CardInstance & {
  lane: Lane
  ready: boolean
  exhausted: boolean
}

type LaneState = {
  threats: FieldCard[]
  defenses: FieldCard[]
}

type GameState = {
  damage: number
  countermeasures: number
  dark: PlayerState
  government: PlayerState

  civicShields: CardInstance[]
  revealedShields: CardInstance[]

  resourceZones: {
    dark: CardInstance[]
    government: CardInstance[]
  }

  field: {
    lanes: {
      earthquake: LaneState
      flood: LaneState
      information: LaneState
    }
  }
}
```

追加するアクション候補:

```ts
type GameAction =
  | { type: "charge"; faction: Faction; instanceId: string }
  | { type: "play"; faction: Faction; instanceId: string; lane?: Lane }
  | { type: "pass"; faction: Faction }
  | { type: "resolve" }
```

ただし、現在のbackend設計と同じく、クライアントから送られた `faction` は信用しません。  
Durable Objectがトークンから役割を判定し、GameCoreに渡します。

## 16. Durable Object / backendへの影響

現在の設計方針はそのまま使えます。

### Durable Objectの責務

- ルームごとの `GameState` を保持する
- プレイヤートークンから役割を判定する
- クライアントのアクションをGameCoreへ渡す
- 更新後の状態をWebSocketで配信する
- 退出、切断、TTLを管理する

### backendで増やす必要がある処理

追加アクションに応じて、`ClientAction` の種類を増やします。

```ts
type ClientAction =
  | { type: "charge"; instanceId: string }
  | { type: "play"; instanceId: string; lane?: Lane }
  | { type: "pass" }
```

DO側では以下を守ります。

- クライアントに相手の手札実体を送らない
- 相手のシールド中身を送らない
- `instanceId` は自分の手札・自分に公開済みのカードだけに限定する
- 不正なフェイズの操作はGameCoreで拒否する
- 同時操作はDO内で直列処理する
- D1は空き部屋一覧だけに使い、ゲーム状態の正本にしない

## 17. 実装順序

一気に入れると破綻しやすいため、以下の順で進めます。

1. `game-core` に防災シールドを追加
2. シールド破壊処理を追加
3. 緊急対応トリガーを自動発動で追加
4. 防災シールドのUIを追加
5. 基盤ゾーンを追加
6. 手札から基盤化するアクションを追加
7. 現場レーンを追加
8. 継続脅威 / 防災ユニットを追加
9. 判定結果の内訳表示を追加
10. バランス調整

最初に実装するべきは防災シールドです。  
理由は、既存のターン構造を大きく壊さずに、ゲームの駆け引きを最も増やせるためです。

## 18. 最初の到達目標

次の状態になれば、カードゲームとしてかなり成立します。

- 闇の組織は災害で防災シールドを割る
- 政府は対策で被害を軽減する
- シールドから緊急対応が出ると逆転が起きる
- 手札を使うか、基盤に置くか悩む
- 場に残る防災ユニットで次ターン以降が有利になる
- どちらかのゲージが100になったらゲーム終了になる

この設計なら、現在のCloudflare Durable Objects構成を維持しつつ、ゲーム性を段階的に強化できます。
